# Android app (Wails v3 mobile, ADR 4)

- `cmd/mobile` (build tag `android`) is the Wails v3 Android app around `mobile.Open`, plus the Bridge service. `internal/adapters/mobile` is the Android wiring on top of desktop's, with no Wails import: the page handler and `Serve`, the API bridge. `mobile/android` is Wails' generated Gradle project.
- Commands: `task mobile:android:build` (`bin/starter.apk`) · `task mobile:android:run` (builds, installs on the connected phone or emulator, starting the first AVD if none is, and opens it).
- Wails v3 mobile is experimental. Building it needs a JDK, the Android SDK, and the NDK (`docs/mobile.md`); `go build ./...` and `task check` skip it. Lint it with `GOOS=android GOARCH=arm64 CGO_ENABLED=1 CC=<NDK clang> golangci-lint run --build-tags android ./cmd/mobile/...`.
- The SPA's `/api` requests go over the Wails bridge (`apiFetch` → `bridgeFetch` → `main.Bridge.Serve` → `mobile.Serve`), because Wails' Android page path turns every request into a body-less `GET` and drops non-200 statuses. `mobile.AssetHandler` answers `/api/*` on the page path with 404, so a request that misses the bridge fails instead of silently succeeding. Don't rename `Bridge` or move it out of `cmd/mobile`'s package `main`: `client.ts` calls it by that name. `apiFetch` checks for `window.wails.invokeAsync` before importing `@wailsio/runtime`, because the import replaces `window.wails`.
- The Android app stays on jsonfile storage.
- `mobile/android` is generated by wails3 with a few hand edits; `docs/mobile.md` says how to regenerate it on upgrade. Its Java package must stay `com.wails.app` (the Go library's JNI names depend on it); only `applicationId` is ours.
- Keep the Wails versions in step (see `.claude/rules/dependencies.md`).
