# REST server and SPA serving

- The server embeds the SPA only when built with `-tags embedweb` after `pnpm build` (`task build` does both). Otherwise `/` shows a hint page.
- The SPA's service worker serves the cached app for offline page loads on any path the Go server serves outside `/api`, so add new server routes (like `/healthz` and `/readyz`) to `navigateFallbackDenylist` in `web/vite.config.ts`. (More on the installable app in `.claude/rules/web.md` and `docs/installable-app.md`.)
- In the local edition, the desktop app keeps its data on the computer (`httpapi.Options.IsDataLocal`), so `GET /api/v1/connection` answers `{"isRequired": false}`. Remote mode leaves `IsDataLocal` unset, so the answer is `true` and the offline notice comes back. The desktop handler answers `/sw.js` with 404, so the service worker never runs there.
- Sign-in (ADR 9, `docs/sign-in.md`) lives under `/auth/`, outside `api/openapi.yaml`, as it is redirects and HTML forms: `GET /auth/sign-in` and `GET /auth/sign-up` redirect to the configured adapter: `/auth/dev` with `Options.IsDevSignInOn`, or, with `Options.SignInProvider` (OIDC), `/auth/oidc` and `/auth/oidc/sign-up`, which set the `oidc_sign_in` attempt cookie (`<state>.<attempt>`, `Path=/auth/oidc`, 10 minutes) and redirect to the provider, which returns to `/auth/oidc/callback` (a refused sign-in is the 400 "Sign-in failed" page, the cause logged). `httpapi` never imports the `oidc` adapter, only its own `SignInProvider` interface. Cookies are `Secure` over TLS or with an `https://` `Options.PublicURL` (`isSecure`). `POST /auth/sign-out` ends the session, locally only. `/auth/` is in `navigateFallbackDenylist`. With `Options.SignIn` set, `sessionMiddleware` puts the session's workspace in the context (from `Authorization: Bearer`, else the `session` cookie; none when signed out, so use cases fail with `ErrNoWorkspace`, a 401), and `refuseCrossSite` (`http.CrossOriginProtection`) refuses cross-origin requests that change something (403 `cross_site`). A new handler needs no sign-in check of its own. `GET /api/v1/session` tells the web app whether sign-in is on and who is signed in.
- The command line's sign-in (RFC 8252, `docs/sign-in.md`), also with `Options.SignIn`: `GET /auth/native` checks `port`, `state`, and `challenge` (a 400 naming each bad one), keeps them in `native_sign_in` (`Path=/auth/native`, 10 minutes), and always goes to sign-in with `return=/auth/native/finish&again=1`, even with a session, so the person chooses who to sign in as (an app's sign-out leaves the browser's session); `/auth/native/finish` issues a one-time code (`IssueSignInCode`, kept hashed in storage, 5 minutes, once) and redirects only to `http://127.0.0.1:<port>/callback`; `POST /auth/native/token` swaps code and verifier for a new session token (JSON), a refused swap being a bare 400. With `sign-up=1`, it goes to `/auth/sign-up` instead. `/auth/sign-in` and `/auth/sign-up` pass `again=1` on; `/auth/oidc?again=1` begins with `SignInProvider.StartAgain` (`prompt=login`) and `/auth/oidc/sign-up?again=1` with `StartSignUpAgain` (`prompt=create` if listed, else `prompt=login`); the web app never sends it, and the dev sign-in ignores it. The sign-in routes honour a `return` path only when it is local (`localPath`), never an open redirect.
- The apps' sign-in in remote mode (ADR 9): with `Options.ClientSignIn` (an interface `httpapi` declares, filled in bootstrap over `clientsignin`, so `httpapi` imports no client adapter), `GET /api/v1/session` answers the hosted server's session with `signInMethod: browser` (the server answers `page`); `POST /api/v1/browser-sign-in` (`isSignUp`) opens the browser through `Options.OpenBrowser`, waits, and answers the session; `DELETE /api/v1/browser-sign-in` cancels it (204), and the waiting `POST` answers a 409 `cancelled` problem (`ErrSignInCancelled`); and `DELETE /api/v1/session` (`endSession`) signs out through it, answering 204 (also on `ErrSessionNotEnded`, which still forgets the token) or a problem. With no `ClientSignIn`, as on the server, both `browser-sign-in` operations and `DELETE /api/v1/session` answer 404. Never answer the apps' window with a redirect: their Wails webview can't follow one (`.claude/rules/desktop.md`), which is why they don't use `POST /auth/sign-out`.
