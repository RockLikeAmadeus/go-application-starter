## Decisions
- **Wails v3**, with the SPA's `/api/*` requests answered in-process by `httpapi.NewHandler` through Wails' asset handler. No port, no bindings, one REST contract. See the parent plan for the rejected options. Record it in `docs/adr/0004-native-shells.md`.
- **All testable wiring lives in `internal/adapters/desktop/`, with no Wails import.** `cmd/desktop/main.go` (`//go:build desktop`) only creates the Wails app and window around `desktop.Open`'s handler. The build tag keeps Wails' cgo/GTK dependency out of `go test ./internal/...`, `task lint` and CI.
- **`desktop.Open(env)` is the seam the acceptance tests drive.** It picks the data folder, opens jsonfile storage through `bootstrap.NewEmbedded`, and returns the app (to close) and the HTTP handler. The desktop driver serves that handler on `httptest` and talks to it with `httpclient`, so the scenarios exercise the same wiring as the real window. (The Wails asset handler is the only part left to the manual check.)
- **The desktop driver uses the real clock**, because `Open` wires `bootstrap.NewEmbedded`. The items steps' `clock.Advance` has no effect there; real nanosecond timestamps keep "oldest first" ordered.
- **Driver routing by tag:** `@desktop` scenarios run only on the desktop driver. The desktop driver runs every feature. Combine each driver's tag filter with the user's `--godog.tags` (`&&`).
- **"Data in use"** is `jsonfile.ErrLocked`, which already exists. The step asserts `errors.Is(err, jsonfile.ErrLocked)`.
- **Data folder:** `STARTER_DATA_DIR` if set, otherwise `<os.UserConfigDir()>/starter`. Pass the user-config-dir lookup in, so the fallback is unit-testable without touching `$HOME`.
- **Out of scope for this step:** remote mode and packaging (AppImage, .deb, .dmg, .msi). Both go to TODO.md as follow-ups when the feature finishes.
- **Keep remote mode open.** The desktop app is meant to run either **local-only** (jsonfile in the data folder) or **connected to a hosted service** (cloud data). Remote mode would be `desktop.Open` choosing `bootstrap.NewRemote` instead of `NewEmbedded`, still behind the same in-process handler: the SPA keeps calling its own `/api`, so the SPA doesn't change and no CORS is needed. Don't build anything this step that assumes local storage outside `desktop.Open`. Later work: forwarding the user's session upstream (accounts/auth TODO items), choosing the mode (env var first; switching inside the app means re-wiring the core while it runs), and choosing the mode only. **There will be no sync between local and cloud data:** a desktop app's data is either local or in the cloud, never both, and switching modes doesn't migrate anything. So remote mode needs no conflict handling, offline queue or merge logic.
- **Offline notice:** the SPA's `OfflineNotice` uses `navigator.onLine`, so a local-only desktop app with the network off would wrongly say it is offline. The rule is **"hide the notice when the API is local"**, not "hide it in the desktop shell": in remote mode a lost connection matters again and the notice must come back. So the Go side reports where the data lives (local or remote), rather than the SPA sniffing for Wails. Settle how at item 6, before its `/red`. The leading option is a small endpoint in `api/openapi.yaml` (e.g. a hypothetical `GET /api/v1/meta` → `{"data": "local" | "remote"}`), so every shell reports it the same way. Remote mode later decides whether the notice tracks the machine's connection or the hosted server being reachable. The check also decides whether the service worker must be skipped in the desktop shell (item 7).
